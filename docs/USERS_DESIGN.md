# Пользователи: регистрация по почте @pgu.ru и хранение файлов — проект (2026-11-02)

Статус: **проект, код не менялся.** Нужны ответы на вопросы в конце, затем — реализация (оценка ниже).

## Как сейчас
- Один вход: имя любое, пароль — `ADMIN_PASSWORD` из `.env`; в сессии хранится только имя.
- Все данные общие: тексты, корпуса, словари, стоп-списки, задачи, а также ручные решения — отметки ✓/✗ вхождений,
  правки разбора (`token_edits`), убранные связи (`relation_overrides`), правки имён (`entity_overrides`, `entity_aliases`).
- Нет таблицы пользователей, нет владельца у данных, нет срока хранения.

## Предлагаемая модель

### Роли
| Роль | Кто | Что может |
|---|---|---|
| **Администратор** | вход по `ADMIN_PASSWORD` (как сейчас) и пользователи, которым админ дал роль | всё; его данные хранятся бессрочно и образуют **общую библиотеку** |
| **Пользователь** | зарегистрировался с адресом `…@pgu.ru` и подтвердил почту | загружает свои тексты и словари, анализирует свои данные и общую библиотеку (только чтение); его данные удаляются через 14 дней |

### Регистрация
1. Форма «Регистрация»: адрес почты, имя (как подписывать), пароль (дважды). Принимаются только адреса, оканчивающиеся
   на `@pgu.ru` (проверка на сервере, без учёта регистра; поддомены — см. вопрос 2).
2. Письмо со ссылкой подтверждения (действует 24 часа). Пока почта не подтверждена — войти нельзя.
3. Вход — по адресу и паролю; «Забыли пароль?» — письмо со ссылкой сброса.
4. Пароли — хеш (argon2/bcrypt), не открытым текстом; ограничение попыток входа и отправки писем (защита от перебора и спама).
5. Отправка писем — через SMTP почтового ящика, который вы укажете (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`,
   `SMTP_PASSWORD`, `SMTP_FROM` в `.env`; без `$` в значениях).
6. Страница администратора «Пользователи»: список, дата регистрации, объём данных, заблокировать / удалить / сделать администратором.

### Владение данными
- Новые поля `owner_id` у текстов, корпусов, словарей, стоп-списков, задач (существующие данные → администратору).
- Пользователь видит: **свои** данные + **общую библиотеку** (данные администраторов) только для чтения.
  Чужие пользовательские данные не видит.
- Ручные решения (✓/✗, правки разбора, убранные связи, правки имён) — пользователь может делать только на своих текстах;
  на общей библиотеке — только администратор (иначе один студент испортит разметку всем).
- Сравнение «с остальной базой» (ключевые слова, TF-IDF и т. п.) у пользователя — по доступным ему текстам.

### Срок хранения: 14 дней
- Отсчёт — от **загрузки** каждого текста / создания словаря (вариант: от последнего входа — вопрос 3).
- На странице «Тексты» и «Словари» у пользователя — «удалится через N дней».
- За 2 дня до удаления — письмо-напоминание (по желанию, вопрос 4).
- Очистка — ежедневная фоновая задача (тот же обработчик): удаляет просроченные тексты со всеми предложениями,
  токенами, вхождениями, именами; пустые корпуса и словари пользователя; освобождает место (`VACUUM` по расписанию).
  Учётная запись остаётся (вопрос 5).
- Администратор может продлить срок отдельному пользователю (по желанию).

### Защита сервера (рекомендую сразу)
- Квота на пользователя: например, 50 текстов / 20 МБ исходников / 2 млн слов одновременно.
- Очередь задач: не больше 2 задач разбора одного пользователя одновременно — чтобы один большой корпус не занимал
  обработчик для всех.

## Оценка трудоёмкости
| Часть | Дни |
|---|---|
| Таблица пользователей, хеши паролей, вход по почте, роли, миграция данных → администратору | 1 |
| Регистрация, подтверждение почты, сброс пароля, SMTP, ограничения попыток | 1–1,5 |
| Владелец у данных и фильтр видимости во всех разделах (тексты, корпуса, словари, анализ, выгрузки, имена, география, семантика, предложения, задачи) | 3–4 |
| Срок хранения: очистка, «удалится через N дней», напоминание | 1 |
| Квоты, справедливая очередь, страница «Пользователи» | 1–1,5 |
| Тесты (особенно «пользователь не видит чужое»), документация | 1–1,5 |
| **Итого** | **≈ 8–10 дней** |

Самая трудоёмкая и рискованная часть — фильтр видимости: сейчас почти каждый запрос считает «все тексты базы».
Делать поэтапно: сначала регистрация и вход (видимость — как сейчас, только администраторы и подтверждённые
пользователи), затем владение данными и очистка.

## Вопросы к пользователю
1. Что видит зарегистрированный пользователь: свои данные + общую библиотеку администратора (только чтение) — или только свои?
2. Адреса: только `@pgu.ru` или и поддомены (`@stud.pgu.ru` и т. п.)?
3. 14 дней — от загрузки каждого файла или от последнего входа пользователя?
4. Предупреждать письмом за 2 дня до удаления?
5. После очистки учётная запись остаётся (можно загрузить заново) — или удалять и её, если пользователь не заходит?
6. С какого ящика отправлять письма (нужны SMTP-адрес, логин и пароль приложения)?
7. Квоты — какие лимиты на пользователя?
