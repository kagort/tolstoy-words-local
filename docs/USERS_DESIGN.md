# Пользователи: гостевой режим и личные кабинеты — проект (2026-11-02, пересмотрен)

Статус: **проект согласован 2026-11-02, реализация — поэтапно.** Английский язык — после запуска сервера
и работы пользователей с русским (решение пользователя).

## Решения пользователя (2026-11-02)
- **Низкий порог входа:** первые пользователи работают **без регистрации**, в гостевом (тестовом) режиме.
- Гостевой режим открыт **любому пользователю из университетской сети**.
- Данные гостя хранятся **3 дня**.
- Если гостю не хватает лимитов или нужно хранить результаты дольше — он отправляет **запрос администратору на
  личный кабинет**.
- В кабинете данные хранятся **14 дней от загрузки** каждого текста / создания словаря; **учётная запись остаётся**
  после очистки файлов.
- Пользователь (гость или кабинет) видит **свои данные + общую библиотеку администратора** (только чтение);
  чужие данные — нет.
- Принимаются адреса почты **только `@pgu.ru`** (без поддоменов) — в запросе на кабинет.
- Регистрация с подтверждением почты, сброс пароля по письму и SMTP-ящик **не нужны** на этом этапе
  (письмо-напоминание за 2 дня заменяется надписью «удалится через N дней»; почту можно добавить позже).

## Как сейчас
- Один вход: имя любое, пароль — `ADMIN_PASSWORD` из `.env`; в сессии хранится только имя.
- Все данные общие: тексты, корпуса, словари, стоп-списки, задачи, а также ручные решения — отметки ✓/✗ вхождений,
  правки разбора (`token_edits`), убранные связи (`relation_overrides`), правки имён (`entity_overrides`, `entity_aliases`).
- Нет таблицы пользователей, нет владельца у данных, нет срока хранения.

## Роли
| Роль | Как попадает | Хранение данных | Что может |
|---|---|---|---|
| **Гость** | открыл сайт из университетской сети — без входа; браузер получает метку гостя (cookie) | **3 дня** от загрузки | загружать свои тексты и словари в пределах гостевых лимитов, анализировать их и общую библиотеку (только чтение) |
| **Личный кабинет** | администратор одобрил запрос и выдал пароль | **14 дней** от загрузки; учётная запись бессрочно | то же, лимиты выше; ✓/✗, правки разбора и имён — на своих текстах |
| **Администратор** | вход по `ADMIN_PASSWORD` (как сейчас) или кабинет с ролью администратора | бессрочно — **общая библиотека** | всё: библиотека, пользователи и запросы, лимиты, ручная разметка библиотеки |

## Гостевой режим
1. Запрос из университетской сети без входа → создаётся гость (строка в таблице пользователей с ролью «гость»),
   браузер получает долгую cookie с его меткой; повторный заход из того же браузера — тот же гость.
2. «Университетская сеть» — список диапазонов адресов в `.env` (`GUEST_NETWORKS=10.0.0.0/8,192.168.0.0/16,…` —
   адреса даёт IT-служба). Адрес берётся из соединения или из заголовка `X-Forwarded-For`, только если запрос
   пришёл через наш Caddy (доверенный прокси) — подделать заголовок снаружи нельзя.
3. Снаружи университетской сети — обычная страница входа (кабинет или администратор); гостевой режим недоступен.
4. Вверху страницы у гостя — плашка: «Гостевой режим: данные хранятся 3 дня и привязаны к этому браузеру.
   Нужно больше — запросите личный кабинет».
5. Очистил cookie / сменил браузер — доступ к прежним гостевым данным теряется (предупреждение в плашке); данные
   удалятся по сроку.

## Запрос личного кабинета
1. Кнопка «Запросить личный кабинет» (в плашке гостя и на странице входа): имя, почта `…@pgu.ru` (проверка
   на сервере, без учёта регистра), цель работы (необязательно).
2. Администратор видит запросы на странице «Пользователи» (счётчик в меню): одобрить / отклонить.
3. При одобрении создаётся кабинет с временным паролем — администратор передаёт его пользователю (почтой или
   лично); при первом входе пароль нужно сменить.
4. Если запрос отправлен из гостевого режима — гостевые данные **переносятся в кабинет** (срок пересчитывается
   на 14 дней от загрузки).
5. Пароли — хеш (argon2/bcrypt); ограничение попыток входа (защита от перебора).

## Владение и видимость данных
- Новое поле `owner_id` у текстов, корпусов, словарей, стоп-списков, задач; существующие данные → администратору
  (общая библиотека).
- Видимость: **свои** + **библиотека** (данные администраторов) только для чтения; чужие гостевые и кабинетные — нет.
  Фильтр во всех разделах: тексты, корпуса, словари, панель выбора и все вкладки анализа, выгрузки, страница
  предложения, имена, география, семантика, задачи, дашборд.
- Ручные решения (✓/✗, правки разбора, убранные связи, правки имён) — только на своих текстах; на библиотеке —
  только администратор (иначе один пользователь испортит разметку всем).
- Сравнение «с остальной базой» (ключевые слова, TF-IDF) — по доступным пользователю текстам.
- Словарь пользователя сопоставляется только с доступными ему текстами; словарь библиотеки с гостевым текстом —
  по запросу гостя (вхождения принадлежат гостю и удаляются вместе с его текстом).

## Лимиты (предварительно — уточнить)
| | Гость | Кабинет |
|---|---|---|
| Текстов одновременно | 10 | 100 |
| Слов во всех текстах | 300 тыс. | 3 млн |
| Размер одного файла | 5 МБ | 50 МБ (как `UPLOAD_MAX_MB`) |
| Свои словари | 3 | 20 |
| Задач разбора одновременно | 1 | 2 |

Лимиты — в `.env`, меняются без пересборки. Превышение — понятное сообщение и ссылка «Запросить личный кабинет».
Очередь: задачи одного пользователя не занимают обработчик целиком — задачи библиотеки и других пользователей идут
по очереди с ними.

## Срок хранения и очистка
- Гость — 3 дня, кабинет — 14 дней от загрузки каждого текста / создания словаря; библиотека — бессрочно.
- На страницах «Тексты» и «Словари» — «удалится через N дней».
- Ежедневная фоновая задача (тот же обработчик): удаляет просроченные тексты со всеми предложениями, токенами,
  вхождениями, именами; пустые корпуса и просроченные словари; гостей без данных старше 3 дней; запускает
  `VACUUM`. Учётные записи кабинетов остаются.
- Администратор может продлить срок кабинету (по желанию).

## Этапы и трудоёмкость
| Этап | Что | Дни |
|---|---|---|
| 1 | Таблица пользователей (гость / кабинет / администратор), гостевая cookie, проверка университетской сети, плашка гостя, вход в кабинет, миграция данных → администратору | 1–1,5 |
| 2 | Владелец у данных и фильтр видимости во всех разделах | 3–4 |
| 3 | Запрос кабинета, страница «Пользователи» (запросы, одобрение, временный пароль, роли, продление), перенос гостевых данных | 1 |
| 4 | Лимиты и справедливая очередь; очистка по сроку и «удалится через N дней» | 1–1,5 |
| — | Тесты (особенно «гость не видит чужое»), документация (USER_GUIDE, DEPLOY: `GUEST_NETWORKS`, лимиты) | 1 |
| | **Итого** | **≈ 7–9 дней** |

Самая трудоёмкая и рискованная часть — этап 2: сейчас почти каждый запрос считает «все тексты базы».
Сервер не открывать гостям, пока не готовы этапы 1–2 и очистка (этап 4).
